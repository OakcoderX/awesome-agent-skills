# Evaluation protocol

This is a developmental smoke test, not a benchmark of general intelligence or a causal estimate of skill effectiveness.

## Frozen inputs

Seven synthetic cases: four substantive reviews (product, business, research, storyboard), then insufficient evidence, a high-stakes medication boundary, and simple arithmetic. The case file was frozen before any response was generated.

- Cases SHA-256: `3d1d18bba10c5a9c5825ea32291e73e0ab0a7c228b29091b5fb6f34031fb26c0`
- Initial rubric SHA-256: `a1981b1773851ed200ef8ae8ef1d3c35157ac3234e2ab095185a5e8a7cebbcfa`
- Original skill source: `f5e95e6fc93a92569bf7c1592a3aebf2462d15f8`, Story Cartographer v2.2

The skill author also authored the cases and rubric. This is a known source of selection bias. Cases were not sampled from a user population, and real user materials were not used.

## Conditions

1. Ordinary assistant reasoning, no additional Socratic instructions.
2. Original Story Cartographer, applied within its stated scope; ordinary reasoning outside that scope. Forcing narrative criteria into business or research would make an unfair baseline.
3. General variant with the applicable adapters; ordinary reasoning for out-of-scope simple requests.

Each condition was generated by a fresh assistant run with the same available model configuration and reasoning-effort setting. The runner did not expose a verifiable exact model version, seed, temperature, or token accounting. No cross-model conclusion is available.

All conditions received the same cases, a target ceiling of 350 words for each substantive review, short/direct instructions for the other cases, and no access to the rubric or other outputs. They could read their condition's instructions and the given facts. No external tools, customer research, paid APIs, deployment, or real-world tests were performed for these synthetic answers.

One assistant context handled all seven cases within each condition. Cases were therefore requested as separate tasks but did not have separate model contexts. There was one response per case and condition, not multiple independent repetitions.

## Review

A fresh reviewer received case text, a predeclared rubric, and responses relabeled independently per case. It was not given the label mapping, conditions, skills, source files, or expected winner. Styles can still reveal a method, so this is label-blind model review rather than guaranteed blinding or human evaluation.

The five 0–2 dimensions are evidence correctness, inference calibration, next-action usefulness, domain fit, and scope control. The rubric concerns observable usefulness, not presence of skill-specific headings. Fatal issues are logged separately. Scores are descriptive checklist judgments; totals must not be marketed as an improvement percentage or statistically meaningful ranking.

## Revision rule

Inspect the actual response artifacts and an independent instruction review. Make a narrow change only when there is a supported failure or contradiction. Preserve the initial results; do not silently replace them with reruns. If runtime instructions change, run new regression cases against the final instructions and identify those separately. Never label a revision held-out if it was designed after seeing the relevant failures.

## Reproduction

- Use [cases.json](cases.json) verbatim with the three conditions above.
- Keep model, runtime constraints, and answer budget comparable.
- Store full responses and the exact instruction snapshot.
- Randomize anonymous labels for every case and keep the mapping from the reviewer.
- Use [rubric.json](rubric.json), retain disagreement and negative results, and publish raw outputs where permission allows.
- Run package checks with `python3 evaluation/validate_package.py`. These checks establish file integrity only.
- For stronger evidence, preregister additional real tasks, use multiple models and repeated runs, and obtain blinded human domain review and observed outcomes.
